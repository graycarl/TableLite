1过程中的六处真实波折

复盘最有价值的部分：这些都不是设计里写好的，而是执行中才暴露的。

① Swift 工具链移除了 func f(): T 旧语法
ImportViewModel.swift:226 · W4 接线期
报错 “Expected '->' after function parameter tuple”，但该行看起来完全合法。agent 逐步二分：先确认不是 Unicode 隐藏字符（od -c）、再手动 brace 平衡、最后写 最小复现 class A { func f(): Int { 1 } } 发现同样失败 → 断定是工具链行为变更，全书统一改 -> T。
② GridRow 与 SwiftUI 撞名
ExportPanelView.swift / SchemaPages.swift · W4
DataGrid 定义了模型类型 GridRow，同模块内 GridRow { … } 优先解析到自家类型而非 SwiftUI.GridRow → 编译失败。解法：所有 SwiftUI 用法显式写 SwiftUI.GridRow，并登记进变更记录。
③ 两个只有真库才暴露的 bug（W3-T9）
冒烟 e2e 才抓到 · 影响编辑主线
bug-1：数值/时间列（charset=63）被误判为二进制 → 主键定位失效，改了也定位不到行。 bug-2：提交路径忽略语句级错误 → 唯一键冲突被当成成功。这印证了「必须有真库 e2e 冒烟」的价值。
④ subagent 余额耗尽（402）
T15 两次尝试
最后一个任务无法委派。agent 先重试一次，确认不可用后 降级为主 session 自己干活，并发现「失败的第一位 agent 其实已改了大部分文件，只是没来得及建偏好面板」→ 直接补缺口，避免重做。
⑤ 跨任务编译冲突只能由集成者修
W2 / W4 集成期
并行 subagent 各自报告「通过」，但合到同一模块后出现 @escaping 缺失、视图 frame 冲突、sheet 不关闭等问题。→ 验证「构建权独占 + 主 session 统一接线」这套契约是必要的，也说明 subagent 的自报不能替代集成验证。
⑥ 演示数据键冲突
最后起测试库时
灌 50 行用户数据时 n 重复导致 email 唯一键冲突，且首次用 2>/dev/null 把错误吞了 → agent 去掉抑制看到真错误，改成 a.n + (b.m-1)*10 生成唯一序号后重灌。

2.2 三层文档在任务契约里的具体用法

specs = 「做到什么算完成」
例：W3-T9 的任务 11 条交付物全部挂在 spec 章节上
• 「行操作（specs/04 §2/§4）：底部＋插入行接真、⌘I 插入、删除行进暂存、行样式新增绿/修改黄/删除红」
• 「可编辑性判定：无主键 → 只读 + specs/04/09 的原因横幅」
• 「菜单接线：⌘↩ 提交 / ⇧⌘P 预览 / ⇧⌘⌫ 放弃，以 specs/02 §9 与 specs/04 为准」
manual = 「长什么样」
每个 UI 任务都指定一页线框图
manual/01-connections、02-workspace、03-data-browsing、04-data-editing、05-filtering、06-query-editor、07-schema-view、08-import-export —— 与 8 个前端任务一一对应，作为控件布局与文案的参照，而不是需求来源。
tech-designs = 「怎么实现」
带章节号的实现规格书
例：T1 的 SQL 生成要求逐条指向 03 §4.2（字面量转义）、10 §4（语句拆分）、08 §3（暂存 SQL）、09 §1.4（LIKE 转义）、07 §3（分页与大字段 LEFT(col,N)）、11 §2（CSV 编解码）。
AGENTS.md = 「不许踩的坑」
直接写进任务硬约束
「NSTextView 智能替换必须全关」（T11）、「截断值绝不能写回库」（T9 + 坑§4）、「libmysqlclient 调用必须在同一串行队列」（T2）、「依赖方向：UI 不得 import CMySQLClient」（所有任务）。

2.3 从文档到决策：六个可追溯的实例

网格只读、编辑只在字段栏
specs/04 §1 · tech 08§8 / 14§1 → S14
文档怎么说：「核心原则」定编辑入口唯一 → 契约怎么写：T9 硬性约束「网格永远只读（S14），所有编辑只在字段栏」→ 代码怎么落：GridCell 四级值模型，网格不提供编辑器。
预览 SQL 必须 == 实际提交
tech 08§4 → S29
文档怎么说：预览与提交要完全一致 → 决策：字面量转义统一走「连接转义器」session.makeEscaper()，纯函数转义只作兜底；T9 交付物第 5 条明确「同一生成路径」→ 登记 S29，成为后续模块的硬约束。
日期时间编辑器：文本框 vs 日期选择器
specs/04 §3 + manual/04 ↔ tech 03§4.3 · S27 → L28
冲突：specs/manual 要「日期选择器 + 手输」，技术设计 S27 定「零时区处理、日期时间原样读写」→ 实现选了纯文本框 → agent 没有改 specs，而是登记 L28 并把「建议改 specs 为文本框」写进交付报告交用户拍板。
无主键表整表只读
specs/04 §2 · tech 08§7 → EditabilityEvaluator
文档怎么说：唯一索引不算数，没有主键就只读 → 实现：T1 先把 Editability/UneditableReason 做成纯逻辑并单测，T9 接上真实判定并展示原因横幅。这是「specs 定义用户可感知行为、tech 定义判定规则」的典型分工。
⌘F 语义折中
specs/05 §1 ↔ 实现新增控件 → L31
specs 说 ⌘F 开关行过滤器面板；实现把 ⌘F 改成上下文分派（表数据标签=开过滤横条并聚焦跨列快速过滤框），而该框是 manual/05 没画的新控件 → 登记 L31，标记为待补 manual/specs。
大字段截断值的安全闸门
